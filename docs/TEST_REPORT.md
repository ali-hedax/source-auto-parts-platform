# گزارش آزمون هداکس

- تاریخ اجرای نهایی: ۲۰۲۶-۱۰-۰۵
- این گزارش فقط نتیجهٔ اجراهای واقعی را ثبت می‌کند. هر چه اجرا نشده با عبارت «اجرا نشده» آمده است.

## ۱. محیط آزمون

| مورد | مقدار |
| --- | --- |
| سیستم‌عامل | Windows 10 Pro (بدون Docker و WSL) |
| Node.js / pnpm | 26.8.2 / 10.34.6 |
| پایگاه داده | PostgreSQL **18.4** واقعی (باینری بومی ویندوز از بستهٔ توسعهٔ `embedded-postgres`)؛ برای هر اجرای آزمون یک خوشهٔ موقت با `TimeZone=Asia/Tehran` روی سرور (عمداً غیر UTC) |
| Docker | Docker Desktop 4.93.0، موتور 29.8.1، Compose 5.5.1، WSL 3.0.1 (هستهٔ WSL 2 با `wsl --update` و تأیید مالک نصب شد). ۸ هسته و حدود ۷٫۶ گیگابایت حافظه برای موتور |
| Redis | Redis 8 در Docker با BullMQ (بخش ۶). در آزمون‌های یکپارچه و اجراکنندهٔ ایزولهٔ بدون Docker، همان handlerها با `QUEUE_DRIVER=inline` اجرا می‌شوند |
| ClamAV | ClamAV 1.5.4 در Docker با پایگاه امضای همراه ایمیج (نسخهٔ 28136، ۲۰۲۶-۰۹-۲۷). **به‌روزرسانی امضا از CDN رسمی از این شبکه مسدود است** (خطای ۴۰۳). دریافت از mirror خصوصی با یک mirror آزمایشی محلی آزموده شد (بخش ۷). آزمون‌های یکپارچه از جایگزین آزمایشی اسکنر استفاده می‌کنند |
| مرورگر | Microsoft Edge (Playwright با `channel: msedge`) |
| رایانه | لپ‌تاپ Intel Core i7-1065G7 (چهار هسته، فرکانس پایهٔ ۱٫۳ گیگاهرتز)، ۱۶ گیگابایت حافظه. در آزمون کارایی، کل پشته (PostgreSQL، API، worker و وب) روی همین رایانه هم‌زمان اجرا می‌شود |
| درگاه پرداخت / پیامک | شبیه‌ساز آزمایشی با برچسب واضح، و **sandbox رسمی زرین‌پال** (`sandbox.zarinpal.com`، بدون پول؛ بخش ۷) / `dev-log`. هر سه در production رد می‌شوند. کاوه‌نگار فقط با آزمون واحد و پاسخ واقعی سرویس به کلید نامعتبر آزموده شد |

\* اجرای قبلی همین مجموعه با به خواب رفتن رایانه قطع شد: ۲ آزمون با `ERR_NETWORK_IO_SUSPENDED` و پایان مهلت شکست خوردند (یکی ۴۲ دقیقه منتظر ماند). همان دو آزمون جداگانه و سپس کل مجموعه دوباره اجرا شد و ۲۸ از ۲۸ پاس شد. عدد جدول از همین اجرای کامل آخر است.

† اجراهای ناموفق پشتهٔ واقعی همه علت مشخص غیرمحصولی داشتند: کش داده از اجرای قبل، انتخابگر مبهم، و یک‌بار build دوبارهٔ بستهٔ domain هم‌زمان با اجرای آزمون (کامپایل دوبارهٔ سرور توسعه و پایان مهلت). در ۲۰۲۶-۱۰-۰۴ اولین اجرای آزمون تازهٔ حساب تجاری شکست خورد، چون خود آزمون جمع خرید را پیش از انتخاب روش ارسال انتظار داشت؛ صفحه جمع را پس از انتخاب روش ارسال نشان می‌دهد. آزمون اصلاح شد. پس از رفع هر کدام، کل مجموعه دوباره اجرا و پاس شد. در ۲۰۲۶-۱۰-۰۵ این اجراها شکست خوردند:

- اولین اجرای انصراف روی sandbox زرین‌پال شکست خورد، چون API کامپایل‌شده پیش از اصلاح نگاشت انصراف ساخته شده بود (build دوباره).
- اجرای بعدی یک اشکال واقعی محصول را آشکار کرد (اشکال ۵۰).
- آزمون تازهٔ همان اشکال یک‌بار با خواب رایانه نامعتبر ماند (۴٫۲ ساعت). یک‌بار هم ترتیب درخواست‌ها را درست نساخته بود و اصلاح شد.
- سپس روی کد قبلی شکست خورد (تأیید اینکه اشکال را می‌گیرد) و روی کد اصلاح‌شده پاس شد.

‡ اجرای قبلی همین روز ۴۷ از ۴۸ بود. مانور بازیابی (A32) به‌دلیل I/O worker یتیم PostgreSQL روی ویندوز شکست خورد، نه اشکال محصول (بخش ۸، ایرادهای زیرساخت آزمون). پس از افزودن `io_method=sync` به آزمون‌های یکپارچه، کل مجموعه دوباره اجرا و ۴۸ از ۴۸ پاس شد.

## ۴. مسیرهای کامل روی پشتهٔ واقعی (وب ← API ← PostgreSQL)

اجراکنندهٔ `pnpm --filter @hedax/web e2e:real` برای هر اجرا یک پشتهٔ تازه می‌سازد: PostgreSQL موقت با migrationها، یک مالک تصادفی و seed توسعه، API و worker کامپایل‌شده (`QUEUE_DRIVER=inline`، بدون Redis) و وب متصل به همان API. پس از آزمون همه را پاک می‌کند. پایگاه دادهٔ توسعه، `.env` و `.local-dev-credentials` خوانده یا تغییر داده نمی‌شوند. این مسیرها همان «تعریف پایان ساخت محلی» بند ۲۲ را پوشش می‌دهند:

- **ورود مالک:** گذرواژه، سپس ثبت اپ احراز هویت (TOTP) با کد واقعی ۶ رقمی، نمایش کدهای بازیابی و ورود به پنل.
- **محصول:** ساخت محصول ایران‌خودرو از پنل، بارگذاری عکس (WebP، بدون EXIF)، انتشار و ثبت شمارش موجودی؛ خریدار مهمان آن را با نام پیدا کرد، عکس را دید («حداکثر ۵ عدد») و به سبد افزود.
- **تأمین و پیش‌فاکتور:** مشتری برای برند BYD با عکس درخواست ثبت کرد؛ worker عکس را اسکن کرد و برای کارکنان قابل دانلود شد؛ مالک پیش‌فاکتور صادر کرد؛ worker دو PDF فارسی و انگلیسی ساخت و مشتری PDF معتبر دریافت کرد؛ مشتری پذیرفت و از درگاه آزمایشی پرداخت کرد («پرداخت تأیید شد.»)؛ سفارش تأمین «در صف تأمین» بود، مالک آن را به «در حال تأمین» برد و مشتری همان را دید.
- **کارکنان:** مالک کارشناس پشتیبانی دعوت کرد؛ کارشناس با لینک یک‌بارمصرف حساب ساخت و وارد شد؛ منوی «کارکنان» برایش نمایش داده نمی‌شود و API همان بخش را با ۴۰۳ رد می‌کند.
- **نرخ ارز و cache:** صفحهٔ کالای درهمی ابتدا با نرخ ۱۶۰٬۰۰۰ باز شد (و cache شد)؛ مالک نرخ ۱۷۰٬۰۰۰ ثبت کرد؛ همان صفحه بی‌درنگ ۱۱٬۰۵۰٬۰۰۰ ریال نشان داد.
- **مرجوعی و استرداد:** خرید کالا، «در حال آماده‌سازی» ← «آمادهٔ ارسال» ← «ارسال‌شده» (روش و کد رهگیری) ← «تحویل‌شده» از پنل؛ درخواست مرجوعی یک عدد؛ تأیید، ثبت دریافت و بازگشت به موجودی، «ثبت درخواست استرداد» با مبلغ پیشنهادی، تأیید و اجرای استرداد؛ اعلان مشتری.
- **صندوق اعلان:** پیش‌فاکتور تازه و تغییر مرحلهٔ تأمین به زبان ساده و بدون کد خام.
- **حساب تجاری (A26):** تعمیرگاه از حساب خود درخواست حساب تجاری داد. مالک در صفحهٔ کالا برای گروه «تعمیرگاه / مشتری تجاری» قیمت ۴٬۰۰۰٬۰۰۰ ریال گذاشت. تا پیش از تأیید، همان مشتری قیمت عمومی ۴٬۸۰۰٬۰۰۰ ریال را دید. مالک درخواست را از «مشتریان» تأیید کرد و نشست قبلی مشتری باطل شد (۴۰۱). پس از ورود دوباره، مشتری قیمت گروه را در صفحهٔ کالا و جمع خرید دید. مهمان همان لحظه قیمت عمومی را دید.
- **نقش سفارشی:** مالک نقش «انباردار» را با سه مجوز ساخت که با توضیح فارسی نمایش داده می‌شوند. کارمند دعوت‌شده با این نقش فقط منوی «موجودی» را دید و دکمهٔ «ثبت شمارش موجودی» را داشت. API محصولات را برای او با ۴۰۳ رد کرد و کارت نقش «۱ عضو» نشان داد.
- **تنظیمات فروشگاه:** روش ارسال تازه با هزینهٔ «۲۵۰٬۰۰۰ ریال» و «۱–۲ روز» ثبت شد و در checkout همان مشتری تجاری ظاهر شد. متن «ارسال» نخست پیش‌نویس ماند و پس از «انتشار» صفحهٔ عمومی `/fa/help/shipping` بی‌درنگ آن را نشان داد. تعطیلی ۱۴۰۵/۰۱/۱۳ به تاریخ شمسی وارد و به‌صورت 2026-04-02 ذخیره شد. تاریخ نادرست ۱۴۰۵/۱۳/۰۱ با نام خودش رد شد و چیزی ارسال نشد.
- **گزارش‌ها:** اعداد صفحهٔ گزارش با پاسخ API یکی بود: وصول و استرداد با تعدادشان، سفارش‌ها به تفکیک وضعیت و اقلام پرفروش. وضعیت‌ها به زبان ساده و همهٔ شمارش‌ها با رقم فارسی بودند.
- **Excel:** دریافت قالب؛ بارگذاری CSV به‌روزرسانی قیمت و موجودی؛ پیش‌نمایش («پیش‌نمایش آماده است»، به‌روزرسانی: ۱، خطا: ۰) موجودی را تغییر نداد؛ «اعمال تغییرات» قیمت و موجودی را تغییر داد.
- **خرید:** جست‌وجو با «فيلتر روغن» (ی عربی)، افزودن به سبد، ورود با OTP (کد توسعه)، ثبت نشانی، انتخاب روش ارسال، پذیرش شرایط، رفتن به درگاه آزمایشی با برچسب «TEST PAYMENT SIMULATOR»، پرداخت موفق، بازگشت به صفحهٔ نتیجه («پرداخت تأیید شد.») و دیدن سفارش `HX-O-…`.
- **تنظیمات، فهرست‌ها، تاریخچه و خروجی:** مدت رزرو با رقم فارسی («۲۰») ذخیره و برگردانده شد. برند خودروی تازه افزوده و نشان «ویژه» به واژه دیده شد. تاریخچهٔ عملیات حساس عملیات همین اجرا را به زبان ساده نشان داد، بدون سرستون انگلیسی و بدون کد خام. پرداخت‌ها با وضعیت «موفق» و برچسب «آزمایشی» دیده شدند. خروجی Excel محصولات یک فایل xlsx واقعی بود.
- **گفت‌وگو:** ورود، ثبت درخواست برای Chery، دیدن آن در «درخواست‌های تأمین» با کد پیگیری، ارسال پیام و باقی ماندن آن پس از بارگذاری دوبارهٔ صفحه.

## ۵. کارایی آزمایشگاهی صفحه‌های عمومی (بند ۱۵)

**روش.** فرمان `pnpm --filter @hedax/web e2e:real -- --perf` وب را با build production (`next build` و `next start`) روی همان پشتهٔ ایزوله اجرا می‌کند، با API و پایگاه دادهٔ واقعی. شرایط اندازه‌گیری:

- مرورگر Edge در نمای موبایل ۳۹۰×۸۴۴.
- CPU چهار برابر کندتر و شبکهٔ ۱٫۶ مگابیت با تأخیر ۱۵۰ میلی‌ثانیه، شبیه «4G کند» در Lighthouse.
- cache خالی مرورگر. پیش از اندازه‌گیری یک درخواست گرم‌کننده فرستاده می‌شود تا راه‌اندازی سرور سنجیده نشود.
- هر صفحه ۵ بار بارگذاری و میانه گزارش می‌شود.

داده‌های خام هر بارگذاری (LCP، عنصر LCP، اولین رنگ‌آمیزی، CLS و منبع جابه‌جایی‌ها، کارهای طولانی، حجم و زمان هر نوع فایل) در [`test-artifacts/perf-lab.json`](test-artifacts/perf-lab.json) است.

**نتیجهٔ نهایی** (۲۰۲۶-۱۰-۰۴، رایانه متصل به برق). هدف مشخصات: LCP حداکثر ۲٫۵ ثانیه و CLS کمتر از ۰٫۱.

**نوسان رایانه (مهم برای خواندن اعداد).** همین کد چند ساعت پیش‌تر روی همین لپ‌تاپ میانهٔ LCP ۲٫۴ ثانیه (صفحهٔ اصلی)، ۱٫۸ ثانیه (جست‌وجو) و ۲٫۵ ثانیه (محصول) داد (۳ بارگذاری). طولانی‌ترین کار رشتهٔ اصلی مرورگر آن زمان ۱ تا ۱٫۴ ثانیه بود و در اجرای نهایی حدود ۰٫۲ ثانیه. علت محتمل، حالت توان پردازنده است (باتری یا گرما). کندسازی چهار برابری CPU این تفاوت را چند برابر می‌کند. بنابراین عدد مطلق LCP روی این رایانه فقط نشانه است. اثر هر تغییر با مقایسهٔ هم‌حالت (A/B) یا شاخص قطعی سنجیده شد: حجم فایل، CLS، و ترتیب و زمان درخواست‌ها. اندازه‌گیری روی گوشی واقعی پس از استقرار در چک‌لیست راه‌اندازی آمده است.

## ۶. استقرار محلی با Docker (۲۰۲۶-۱۰-۰۴)

ایمیج‌ها با `infra/docker/Dockerfile` ساخته شدند (api، worker با Chromium، web به‌صورت standalone و tools). همه با `infra/docker-compose.yml` و Caddy روی `https://localhost` اجرا شدند. Caddy برای `localhost` از CA محلی خودش گواهی می‌دهد. هر مرحله در یک پروژهٔ Compose جدا اجرا شد و هیچ دادهٔ موجودی پاک نشد.

**حالت production** (`APP_ENV=production`، پرداخت و پیامک `none`):

| بررسی | نتیجه |
| --- | --- |
| build همهٔ ایمیج‌ها | پاس، پس از رفع اشکال ۴۰ |
| migration، ساخت نخستین مالک، سلامت سرویس‌ها | پاس؛ همه healthy |
| readiness | `database`، `redis`، `storage` و `scanner` (موتور `clamav`) برابر `up`؛ `searchLocale` برابر `ok` |
| صفحه‌ها از راه Caddy | `/fa` با RTL و `/en` با LTR (۲۰۰)، `/parts` → `/fa/parts`، http → https، سرآیندهای HSTS، `nosniff`، `DENY` و `Referrer-Policy` |
| مرورگر | ورود مالک و ثبت TOTP؛ ساخت دسته، کالا و عکس، انتشار و دیدن عکس از `/media`؛ Excel با اسکن واقعی؛ رد EICAR (۳ از ۳ پاس) |
| صف پس‌زمینه | ۴ رویداد (دو اسکن، خواندن و اعمال Excel) با یک تلاش از راه BullMQ و Redis انجام شدند |
| پشتیبان‌گیری و بازیابی | پاس، غیرمخرب (A32) |

**حالت توسعه روی همان ایمیج‌ها** (دادهٔ نمونه، درگاه آزمایشی، پیامک توسعه، با همان Redis/BullMQ، ClamAV و Caddy): **همهٔ ۱۵ آزمون مرورگری پاس شدند (۲٫۲ دقیقه).** این شامل ساخت PDF پیش‌فاکتور با Chromium در کانتینر worker، چت زنده از راه Caddy، پرداخت آزمایشی، ابطال cache صفحهٔ عمومی در build standalone و رد EICAR است.

یک اجرای ناموفق علت محیطی داشت. دادهٔ نمونه پیش از ساخت مالک بارگذاری شده بود، پس نرخ نمونه ثبت نشد و آزمون نرخ و خرید درهمی شکست خوردند. ترتیب درست شد و `seed-dev` حالا در این وضعیت صریحاً هشدار می‌دهد. یک اجرای دیگر روی ایمیج‌های بعدی، اعلان بدون متن تصمیم مرجوعی (اشکال ۴۹) و یک race در خود آزمون را نشان داد. پس از رفع، ایمیج‌ها دوباره ساخته شدند و **روی ایمیج‌های نهایی هر ۱۵ آزمون پاس شدند** (۲٫۲ دقیقه). تصاویر بررسی بصری این بخش از همین اجرا و از build production هستند.

## ۷. درگاه زرین‌پال، پیامک کاوه‌نگار، امضای ClamAV و پشتیبان خودکار (۲۰۲۶-۱۰-۰۵)

**درگاه زرین‌پال.** آزمون واحد (`apps/api/test/unit/payment-sms-adapters.test.ts`) این موارد را با پاسخ‌های ساختگی REST v4 می‌آزماید:

- درخواست پرداخت و نشانی StartPay در sandbox و درگاه اصلی؛
- تأیید کد ۱۰۰ و ۱۰۱ با همان مبلغ؛
- پرداخت‌نشده (‎-51) و `IN_BANK` (در انتظار)؛
- انصراف (`NOK`)، `FAILED` و `REVERSED`؛
- تطبیق بدون callback؛
- مبلغ نابرابر (‎-50 با وضعیت `PAID`)، که هرگز موفق ثبت نمی‌شود؛
- پاسخ غیر JSON؛
- نبود مبلغ مورد انتظار؛
- guardهای production.

**اجرای واقعی روی sandbox رسمی زرین‌پال.** اجراکنندهٔ ایزوله با `E2E_PAYMENT=zarinpal-sandbox` اجرا شد: پشتهٔ واقعی وب ← API ← PostgreSQL، با مرچنت تصادفی که sandbox می‌پذیرد. مرورگر روی صفحهٔ واقعی `sandbox.zarinpal.com/pg/StartPay/…` دکمهٔ «پرداخت» یا «انصراف» را زد:

| مسیر | نتیجه |
| --- | --- |
| خرید کالای موجود و پرداخت | پاس: verify کد ۱۰۰، «پرداخت تأیید شد.»، سفارش `HX-O-…` |
| انصراف در درگاه، سپس تلاش دوباره | پاس: «پرداخت لغو شد.»، تلاش تازه، «پرداخت تأیید شد.» |
| پاسخ دیررس checkout (اشکال ۵۰) و گفت‌وگوی درخواست تأمین | پاس |
| پیش‌فاکتور: پذیرش و پرداخت در مسیر پنل مدیریت | پاس (اجرای جدا با همان تنظیم) |

رفتار مشاهده‌شدهٔ sandbox که در adapter لحاظ شد: پس از «انصراف»، verify کد ‎-51 می‌دهد ولی استعلام تا مدتی `IN_BANK` می‌ماند (اشکال ۵۵).

**پیامک کاوه‌نگار.** آزمون واحد این موارد را پوشش می‌دهد:

- `verify/lookup` با قالب و شمارهٔ محلی `09…`؛
- `sms/send` با خط اختیاری؛
- کدهای خطای ۴۱۸، ۴۲۴ و ۴۰۳؛
- خطای شبکه بدون ثبت نشانی، چون کلید درون URL است؛
- رد کد و قالب نامعتبر.

یک درخواست به سرویس واقعی کاوه‌نگار با کلید ساختگی، پاسخ ۴۰۳ گرفت. adapter آن را `KAVENEGAR_403` گزارش کرد. **ارسال واقعی پیامک اجرا نشده است** (کلید و قالب تأییدشده لازم است).

**امضای ClamAV.**

- **پاسخ clamd:** پاسخ `VERSION` به شکل `ClamAV 1.5.4/28136/Sun Sep 27 06:26:12 2026` است، از کانتینر واقعی، و آزمون واحد دارد. readiness از روی آن `scannerSignatures`، نسخه و سن امضا را می‌دهد. **این فیلدها هنوز روی ایمیج‌های Docker تازه بررسی نشده‌اند.**
- **mirror خصوصی:** یک کانتینر رسمی `clamav/clamav:stable` با پایگاه خالی و تنظیم `PrivateMirror` از فایل `infra/docker-compose.clamav-mirror.yml` اجرا شد. mirror آزمایشی محلی فایل‌های امضاشدهٔ همان volume را سرو می‌کرد. freshclam پایگاه‌های `daily` (28136)، `main` (63) و `bytecode` (339) را گرفت. هر سه با «Database test passed» پذیرفته شدند. mirror واقعی بیرون از منطقهٔ مسدود هنوز تهیه نشده است.

**سرویس پشتیبان خودکار (`--profile backup`).** همه روی Docker محلی اجرا شد. پایگاه دادهٔ نسخهٔ بررسی فقط خوانده شد و فایل‌ها فقط‌خواندنی بودند.

**ایرادهای زیرساخت آزمون (نه محصول):** داده‌کش `next dev` پاسخ API یک پایگاه موقت قبلی را یک‌بار (stale-while-revalidate) به اجرای بعدی داد و شناسهٔ کالای قدیمی به سبد رفت؛ اجراکنندهٔ ایزوله حالا کش fetch را پیش از هر اجرا پاک می‌کند. در آزمون حلقهٔ worker، متغیر محیطی پس از بارگذاری کش‌شدهٔ env تنظیم شده بود؛ حالا پیش از راه‌اندازی تنظیم می‌شود. یک انتخابگر مبهم Playwright (دو لینک به یک پیش‌فاکتور) دقیق‌تر شد. در ۲۰۲۶-۱۰-۰۴ یک فرایند I/O worker یتیم از PostgreSQL 18 موقت روی ویندوز پس از توقف، درگاه 55435 را باز نگه داشت و اجرای بعدی شروع نشد. اجراکننده حالا PostgreSQL موقت را با `io_method=sync` و بدون I/O worker اجرا می‌کند. در ۲۰۲۶-۱۰-۰۵ همین مشکل در مانور بازیابی آزمون یکپارچه (A32) رخ داد. آن آزمون PostgreSQL را متوقف و روی دادهٔ بازیابی‌شده با همان درگاه دوباره روشن می‌کند. I/O worker یتیم درگاه را نگه داشت و روشن شدن دوباره شکست خورد («Unknown Error: undefined»). نتیجهٔ آن اجرا ۴۷ از ۴۸ بود. آزمون‌های یکپارچه حالا هم `io_method=sync` دارند.

## ۹. موارد اجرانشده یا محدود

**گیر متناوب در آزمون یکپارچه:** در ۳ اجرا از حدود ۱۲ اجرای کامل در یک بازهٔ زمانی، یک درخواست HTTP درون آزمون چند دقیقه طول کشید (یک‌بار ۲۲۲ ثانیه) و سپس موفق برگشت. در همان زمان درخواست‌های دیگر کند نبودند و انتظار قفل پایگاه داده‌ای ثبت نشد. پس از افزودن اندازه‌گیری دقیق (زمان هر پرس‌وجو، انتظار pool و زمان پردازش سرور) در ۷ اجرای کامل بعدی تکرار نشد. علت هنوز نامعلوم است و ابزار اندازه‌گیری فعال مانده است.

## ۱۱. اجرای دوبارهٔ آزمون‌ها

```bash
pnpm install
pnpm build
pnpm test                                        # واحد (worker به Edge/Chrome یا PDF_BROWSER_EXECUTABLE نیاز دارد)
pnpm --filter @hedax/api test:integration        # PostgreSQL موقت خودکار
pnpm e2e                                         # مرورگر با دادهٔ پیش‌نمایش (Edge؛ PW_CHANNEL=chrome)
```

آزمون پشتهٔ واقعی (پورت‌های 55435، 4100 و 3300 باید آزاد باشند؛ پیش از آن `pnpm build`):

```bash
pnpm --filter @hedax/web e2e:real
# تصاویر بررسی بصری:  E2E_SCREENSHOTS_DIR=<مسیر>/docs/test-artifacts/ui pnpm --filter @hedax/web e2e:real
# روی sandbox رسمی زرین‌پال (اینترنت لازم؛ بدون پول):  E2E_PAYMENT=zarinpal-sandbox pnpm --filter @hedax/web e2e:real
```

برای اجرای همان آزمون‌ها روی پشته‌ای که خودتان بالا آورده‌اید: `E2E_REAL_BASE_URL=<آدرس وب> npx playwright test -c playwright.real.config.ts` در `apps/web`. آزمون‌های پنل مدیریت فقط با اجراکنندهٔ ایزوله اجرا می‌شوند، چون به مالکی تازه نیاز دارند که TOTP را در آزمون ثبت کند.
