# استقرار سورس | Source

> **وضعیت:** پیکربندی Docker (`infra/`) نوشته شده ولی در محیط ساخت **اجرا نشده است**، چون Docker و WSL نصب نبودند. پیش از استقرار واقعی، بخش «آزمون پذیرش استقرار» را روی سرور هدف اجرا کنید. خرید سرور، دامنه یا هر سرویس پولی بر عهدهٔ مالک است.

## ۱. معماری پیشنهادی (بند ۱۸)

- یک سرور لینوکسی (VPS) با Docker و امکان افزایش منابع، به‌اضافهٔ **ذخیره‌ساز شیء** برای فایل‌ها (اختیاری در شروع) و **نسخهٔ پشتیبان بیرون از سرور اصلی**.
- سرویس‌ها: `caddy` (HTTPS)، `web` (Next.js)، `api` (NestJS + WebSocket)، `worker` (صف، PDF)، `postgres` 18، `redis` 8 و `clamav`. فقط Caddy پورت ۸۰/۴۴۳ را باز می‌کند.
- **برآورد اولیهٔ منابع، نه تضمین:** ۴ vCPU، ۸ GB RAM و ۸۰ GB SSD. ClamAV حدود ۲ تا ۳ GB حافظه می‌خواهد و Chromium هنگام ساخت PDF حافظه مصرف می‌کند. ظرفیت واقعی را آزمون بار با دادهٔ نمونه تعیین می‌کند.
- محل و ارائه‌دهندهٔ سرور را با این معیارها انتخاب کنید: دسترسی واقعی کاربران ایران، شرایط درگاه پرداخت و پیامک (مثلاً محدودیت IP یا محل سرور برای callback)، شرایط سرویس و بودجه.

## ۲. پیش‌نیاز روی سرور

1. Docker Engine و Docker Compose v2؛ ساعت سرور همگام (NTP).
2. رکورد DNS از نوع A/AAAA برای دامنه به IP سرور؛ پورت‌های ۸۰ و ۴۴۳ باز؛ دیوار آتش برای بقیهٔ پورت‌ها بسته؛ ورود SSH فقط با کلید.
3. کلون مخزن روی سرور.

## ۳. پیکربندی

از `.env.example` فایل `.env` بسازید (کنار ریشهٔ مخزن، بیرون از git):

| متغیر | مقدار production |
| --- | --- |
| `APP_ENV` | `production` |
| `HEDAX_DOMAIN` | دامنهٔ نهایی، مثلاً `shop.example.ir` |
| `PUBLIC_BASE_URL` | `https://<دامنه>` |
| `ACME_EMAIL` | ایمیل مدیر برای گواهی TLS (**الزامی**؛ بدون آن Caddy اجرا نمی‌شود و Compose با پیام روشن متوقف می‌شود) |
| `POSTGRES_PASSWORD` | رمز تصادفی بلند |
| `SESSION_SECRET`، `OTP_PEPPER`، `APP_ENCRYPTION_KEY` | هر کدام ۳۲ بایت تصادفی base64؛ **جداگانه و امن نگهداری شوند** (بدون `APP_ENCRYPTION_KEY` رمز TOTP کارکنان پس از بازیابی خوانا نیست) |
| `STORAGE_DRIVER` | `local` (حجم `storage`) یا `s3` با متغیرهای `S3_*` و `PUBLIC_MEDIA_BASE_URL` به آدرس عمومی bucket |
| `PAYMENT_PROVIDER` | `none` تا زمانی که adapter درگاه واقعی نوشته و آزموده شود؛ شبیه‌ساز در production رد می‌شود |
| `SMS_PROVIDER` | `none` تا اتصال سرویس پیامک؛ ورود مشتری با OTP تا آن زمان ممکن نیست |
| `REVALIDATE_SECRET` | ۳۲ بایت تصادفی base64. API و worker پس از تغییر کالا، قیمت، موجودی، نرخ یا متن‌ها با این راز از وب می‌خواهند cache صفحات عمومی را فوراً تازه کند (Compose نشانی داخلی `http://web:3000` را خودش می‌دهد) |

Compose این مقادیر را خودش تنظیم می‌کند: `COOKIE_SECURE=true`، `OPENAPI_ENABLED=false`، `TRUST_PROXY=true`، `MALWARE_SCANNER=clamav`. در production، اجرا با شبیه‌ساز، پیامک توسعه، «بدون اسکن»، صف درون‌فرایندی (`QUEUE_DRIVER=inline`)، کوکی ناامن، آدرس http یا OpenAPI عمومی ممتنع است. مقدار پیش‌فرض `QUEUE_DRIVER` همان `bullmq` است و نیازی به تنظیم ندارد.

## ۴. راه‌اندازی

همهٔ فرمان‌ها از ریشهٔ مخزن اجرا می‌شوند:

```bash
COMPOSE="docker compose -f infra/docker-compose.yml --env-file .env"

$COMPOSE build
$COMPOSE up -d postgres redis clamav           # اولین اجرای ClamAV چند دقیقه طول می‌کشد
$COMPOSE run --rm tools                        # prisma migrate deploy
# اولین مالک (seed پایه هم اجرا می‌شود؛ رمز فقط از متغیر محیطی)
read -s HEDAX_OWNER_PASSWORD && export HEDAX_OWNER_PASSWORD
$COMPOSE run --rm -e HEDAX_OWNER_PASSWORD tools node dist/cli/bootstrap-owner.js --email owner@your-domain --name "نام مالک"
unset HEDAX_OWNER_PASSWORD
$COMPOSE up -d
```

- **دادهٔ نمونه (`seed-dev`) را روی production اجرا نکنید**؛ در `APP_ENV=production` اجرا رد می‌شود.
- پس از اولین ورود مالک در `https://<دامنه>/fa/staff/login`، ثبت TOTP اجباری است.
- سپس در پنل این موارد را کامل کنید: شرایط فروش و سیاست‌ها (منتشرشده)، روش‌های ارسال، نرخ تبدیل، تقویم کاری، اطلاعات تماس تأییدشده و مالیات. چک‌لیست کامل در [`LAUNCH_CHECKLIST.md`](LAUNCH_CHECKLIST.md) است.

## ۵. آزمون پذیرش استقرار (پیش از باز کردن سایت)

```bash
$COMPOSE ps                                                   # همه healthy
$COMPOSE exec api node -e "fetch('http://127.0.0.1:4000/health/ready').then(r=>r.json()).then(j=>console.log(JSON.stringify(j)))"
```

باید `database`، `redis` و `storage` برابر `up`، `searchLocale` برابر `ok` و `scanner` برابر `up` باشد. سپس:

1. `https://<دامنه>/fa` و `/en` باز شوند و `/parts` به `/fa/parts` هدایت شود.
2. یک محصول با عکس ساخته و منتشر شود و عکس در فروشگاه دیده شود.
3. بارگذاری یک PDF در گفت‌وگو پس از اسکن «آماده» شود و فایل EICAR آزمایشی «رد» شود.
4. یک پیش‌فاکتور ارسال شود و PDF فارسی و انگلیسی آن ساخته شود.
5. چت دوطرفه در دو مرورگر زنده باشد (WebSocket از مسیر `/api/v1/ws`).
6. پشتیبان‌گیری و بازیابی آزمایشی طبق [`BACKUP_RESTORE.md`](BACKUP_RESTORE.md) اجرا شود.

**نتیجهٔ اجرای محلی (۲۰۲۶-۱۰-۰۴، Docker Desktop، `HEDAX_DOMAIN=localhost`):**

- همهٔ ایمیج‌ها ساخته شدند و همهٔ سرویس‌ها سالم بالا آمدند.
- readiness برای پایگاه داده، Redis، ذخیره‌ساز و اسکنر (`clamav`) «up» و برای جست‌وجوی فارسی «ok» بود.
- مورد ۱ پاس شد: `/fa` و `/en` با جهت درست، هدایت `/parts`، هدایت http به https، و سرآیندهای HSTS، `nosniff` و `DENY`.
- مورد ۲ پاس شد: ورود مالک با ثبت TOTP، ساخت دسته، ساخت کالا با عکس، انتشار و دیدن عکس در فروشگاه.
- مورد ۳ پاس شد:
  - فایل سالم پس از اسکن ClamAV «آماده» شد.
  - فایل آزمایشی EICAR با `MALWARE_DETECTED` رد شد و ذخیره نشد.
  - رویدادها از راه BullMQ و Redis پردازش شدند.
- مورد ۶ پاس شد (`BACKUP_RESTORE.md` بخش ۴).
- موارد ۴ و ۵ (PDF پیش‌فاکتور و چت زنده) در حالت توسعه روی همین ایمیج‌ها با کل آزمون مرورگری پاس شدند. حالت production ورود مشتری و پرداخت ندارد (`SMS_PROVIDER` و `PAYMENT_PROVIDER` برابر `none`).
- **روی سرور هدف هنوز اجرا نشده است.**

**به‌روزرسانی امضای ClamAV:** از شبکهٔ محیط ساخت، CDN رسمی ClamAV درخواست `freshclam` را با خطای ۴۰۳ رد کرد («Blocked by CDN»، منطقهٔ مسدود). ClamAV با پایگاه امضای همراه ایمیج اجرا شد، ولی این پایگاه کهنه می‌شود. پیش از راه‌اندازی یکی از این راه‌ها لازم است:

- mirror خصوصی، مثلاً با ابزار رسمی `cvdupdate` روی سروری بیرون از منطقهٔ مسدود؛
- یا سرور در منطقه‌ای که مسدود نیست.

**اتصال به mirror خصوصی:** نشانی mirror را در `CLAMAV_PRIVATE_MIRROR` بگذارید و فایل افزودنی `infra/docker-compose.clamav-mirror.yml` را بعد از فایل اصلی بیاورید:

```bash
docker compose -f infra/docker-compose.yml -f infra/docker-compose.clamav-mirror.yml --env-file .env up -d clamav
```

- این فایل `PrivateMirror` را در `freshclam.conf` ایمیج رسمی تنظیم می‌کند. این تنظیم جای `DatabaseMirror` را می‌گیرد.
- mirror فقط باید فایل‌های `main`، `daily` و `bytecode` (`.cvd` یا `.cld`) و فایل‌های `.sign` آن‌ها را بدون تغییر سرو کند. این فایل‌ها امضای ClamAV دارند و freshclam هر کدام را پیش از استفاده آزمایش می‌کند.
- **آزموده (۲۰۲۶-۱۰-۰۵):** یک freshclam با پایگاه خالی، هر سه پایگاه را از یک mirror آزمایشی محلی دریافت کرد. این mirror همان فایل‌های امضاشدهٔ volume را سرو می‌کرد. هر سه با «Database test passed» پذیرفته شدند. یک mirror واقعی بیرون از منطقهٔ مسدود هنوز تهیه نشده است.
- اسکریپت راه‌اندازی ایمیج برای نشانی‌های دارای `/` پیام `sed: bad option in substitution expression` چاپ می‌کند. این پیام بی‌اثر است و تنظیم درست به انتهای `freshclam.conf` افزوده می‌شود.

**پایش سن امضاها:** readiness (`/health/ready`) علاوه بر در دسترس بودن اسکنر، سن پایگاه امضا را هم گزارش می‌کند:

- `scannerSignatures` یکی از `fresh`، `stale`، `unknown` یا `not-applicable` است. `stale` یعنی امضاها از `CLAMAV_SIGNATURE_MAX_AGE_HOURS` (پیش‌فرض ۴۸ ساعت) قدیمی‌ترند.
- `scannerSignatureVersion` و `scannerSignatureAgeHours` نسخه و سن امضاها را نشان می‌دهند.
- امضای کهنه readiness را ناموفق نمی‌کند، چون اسکن هنوز کار می‌کند. ولی بدافزار تازه را نمی‌شناسد، پس برای `stale` هشدار بگذارید (بخش ۷). داشبورد پنل همین را با ردیف «به‌روز بودن امضای ضدویروس» و برچسب «نیاز به بررسی» نشان می‌دهد.

## ۶. امنیت عملیاتی

- PostgreSQL، Redis، ClamAV و ذخیره‌ساز خصوصی هیچ پورت عمومی ندارند (فقط شبکهٔ داخلی Compose).
- `.env` با دسترسی `600` و مالک کاربر سرویس؛ هیچ رازی در image یا git نیست (`.dockerignore`).
- به‌روزرسانی منظم سیستم‌عامل و imageها؛ نسخهٔ Node و پایگاه داده پین شده‌اند.
- لاگ‌ها JSON و چرخشی‌اند (هر سرویس ۵×۱۰MB). لاگ درخواست بدنه، کوکی یا دادهٔ شخصی ندارد.
- مسیر `/health` از اینترنت در دسترس نیست و بررسی سلامت داخل شبکهٔ Docker انجام می‌شود.

## ۷. پایش و هشدار

حداقل این‌ها هشدار داشته باشند: خطای readiness، امضای کهنهٔ ضدویروس (`scannerSignatures` برابر `stale` یا `unknown`)، پر شدن دیسک (بیش از ۸۰٪)، توقف صف (رویداد outbox در وضعیت `PENDING` قدیمی‌تر از چند دقیقه)، شکست پشتیبان‌گیری، انقضای گواهی TLS و ناهمگامی ساعت سرور. پرونده‌های باز پرداخت در داشبورد دیده می‌شوند.

## ۸. به‌روزرسانی نسخه

```bash
git pull
$COMPOSE build
$COMPOSE run --rm tools          # migrationهای جدید (افزایشی)
$COMPOSE up -d
```

پیش از هر به‌روزرسانی پشتیبان بگیرید. migrationها افزایشی نوشته شده‌اند. برای بازگشت، image قبلی را اجرا کنید و در صورت نیاز پایگاه داده را از پشتیبان بازیابی کنید.

## ۹. اتصال درگاه و پیامک واقعی

هر دو اتصال پشت یک interface ثابت هستند. اگر ارائه‌دهندهٔ دیگری انتخاب شود، فقط adapter همان ارائه‌دهنده نوشته می‌شود و بقیهٔ سامانه تغییری نمی‌کند.

### درگاه پرداخت: زرین‌پال (adapter آماده)

1. در پنل زرین‌پال درگاه بسازید. دامنهٔ ثبت‌شده باید همان `HEDAX_DOMAIN` باشد. زرین‌پال callback را فقط برای دامنهٔ ثبت‌شده می‌پذیرد.
2. در `.env` سرور تنظیم کنید:
   - `PAYMENT_PROVIDER=zarinpal`
   - `PAYMENT_MERCHANT_ID=<مرچنت ۳۶ نویسه‌ای>`
   - `ZARINPAL_SANDBOX=false`
3. آدرس بازگشت را سامانه خودش می‌سازد: `https://<دامنه>/api/v1/payments/callback/zarinpal`. تنظیم جداگانه در پنل لازم نیست.
4. مبلغ‌ها ریالی‌اند و با `currency: IRR` ارسال می‌شوند. هیچ تبدیلی به تومان یا ضرب در ۱۰ انجام نمی‌شود.
5. موفقیت فقط با verify سرور به سرور ثبت می‌شود (کد ۱۰۰ یا ۱۰۱ برای همان مبلغ و همان مرچنت). callback فقط شناسه است. پرداختی که مشتری پس از آن برنگشت، با inquiry در job تطبیق کامل می‌شود.
6. **استرداد:** API استرداد زرین‌پال نیازمند توکن دسترسی جداگانه است و در نسخهٔ اول وصل نشده است. استرداد در پنل زرین‌پال انجام می‌شود و کد پیگیری آن در «استردادها» به‌صورت «مرجع دستی» ثبت می‌شود.
7. **پیش از فعال‌سازی:** یک خرید و یک پرداخت پیش‌فاکتور با مبلغ کم روی دامنهٔ واقعی انجام و سپس مسترد شود. همین مسیرها در sandbox رسمی زرین‌پال آزموده شده‌اند (`docs/TEST_REPORT.md`). در development می‌توانید `ZARINPAL_SANDBOX=true` و یک UUID دلخواه به‌عنوان مرچنت بگذارید؛ این حالت در production رد می‌شود.

### پیامک: کاوه‌نگار (adapter آماده)

1. در پنل کاوه‌نگار یک **قالب تأیید** (verify/lookup) بسازید و منتظر تأییدش بمانید. متن قالب باید `%token` داشته باشد؛ همان کد ورود است.
2. در `.env` سرور تنظیم کنید:
   - `SMS_PROVIDER=kavenegar`
   - `KAVENEGAR_API_KEY=<کلید API>`
   - `KAVENEGAR_OTP_TEMPLATE=<نام قالب>`
3. اعلان‌های متنی (ارسال سفارش، پیش‌فاکتور و…) با `sms/send` فرستاده می‌شوند. اگر خط اختصاصی دارید، `KAVENEGAR_SENDER` را تنظیم کنید؛ وگرنه خط پیش‌فرض حساب استفاده می‌شود. خاموش‌کردن پیامک هر نوع اعلان در «تنظیمات» پنل است.
4. کلید API در مسیر URL کاوه‌نگار است. سامانه هیچ URL یا خطای خام شبکه را در لاگ نمی‌نویسد و فقط کد وضعیت کاوه‌نگار را ثبت می‌کند. چند کد مهم:
   - ۴۱۸: اعتبار کافی نیست.
   - ۴۲۴: قالب پیدا نشد یا تأیید نشده است.
   - ۴۰۳: کلید نامعتبر است.
5. محدودیت نرخ OTP در production در Redis فعال است.
